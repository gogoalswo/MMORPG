# 웹 MMORPG 개발 계획

> 목표: 브라우저에서 도는 실시간 멀티플레이 MMORPG.
> 그래픽 레퍼런스: 로우폴리 3D + 고정 쿼터뷰(유사 아이소메트릭) + 머리 위 이름/HP바 오버레이.

---

## 0. 레퍼런스 그래픽 분석

스크린샷에서 읽히는 기술 요소 (= 우리가 구현해야 할 목록):

| 요소 | 관찰 | 구현 방법 |
|---|---|---|
| 카메라 | 원근감이 약한 쿼터뷰. 완전 직교는 아님 | Perspective, **FOV 25~35°**, pitch 50~55°, 거리 30~50m (좁은 FOV로 아이소 느낌) |
| 건물 | 하프팀버(목조 뼈대) 저폴리, 텍스처 거의 없음 | 모듈러 킷(벽/지붕/문/창) + 버텍스 컬러 or 팔레트 아틀라스 1장 |
| 라이팅 | 단일 태양광 + 부드러운 그림자, 무채색 앰비언트 | DirectionalLight 1개 + Hemisphere, PCFSoft 그림자맵 2048, 카메라 주변만 커버하는 타이트 프러스텀 |
| 재질 | PBR 아님. 채도 낮은 매트 | MeshLambert / 커스텀 툰 셰이더, metalness 0 |
| 풀/수풀 | 대량의 얇은 잎, 바람 흔들림 | InstancedMesh 십자 쿼드 + alphaTest + 버텍스 셰이더 바람, 거리 페이드 |
| 지면 | 흙길과 잔디의 부드러운 경계 | 스플랫맵 기반 터레인 셰이더(4채널 블렌딩) |
| 이름표 | 캐릭터 위 흰 텍스트 + 빨간 HP바 | HTML 오버레이(projectToScreen) — 화면 밖/거리 초과 컬링 |
| 대화 | 상단 말풍선/대사창 | 순수 DOM UI |

**핵심 판단**: 이 비주얼은 Three.js로 충분히 재현 가능하고, 오히려 저폴리라서 브라우저 성능에 유리합니다. 유니티 WebGL은 초기 로딩(수십 MB WASM)과 모바일 메모리 때문에 비추천.

## 1. 기술 스택

### 클라이언트
- **TypeScript + Vite**
- **Three.js** (렌더링) — react-three-fiber는 선택. MMO UI가 React면 R3F가 편하지만, 렌더 루프 제어는 순수 Three가 단순함. → **순수 Three.js + React는 UI 오버레이만** 권장
- **React** — 인벤토리/채팅/퀘스트/상점 등 HTML UI
- 에셋: **glTF(.glb)** + Draco/meshopt 압축, 텍스처는 **KTX2(basis)**
- 상태: zustand (가벼운 클라 상태)

### 서버
- **Node.js + TypeScript**, 권위(authoritative) 서버
- **Colyseus** — 룸/상태동기화 프레임워크. 스키마 기반 바이너리 델타 전송이 내장이라 MMO 첫 구현에 시간을 크게 아낌
  - 대안: uWebSockets.js + 직접 만든 바이너리 프로토콜 (더 빠르지만 개발비용 3~4배)
- **PostgreSQL** — 계정/캐릭터/아이템/퀘스트 진행
- **Redis** — 세션, 접속자 presence, 노드 간 pub/sub, 레이트리밋
- **Prisma** or Drizzle (ORM)

### 인프라
- Docker Compose(로컬) → Fly.io / Railway / AWS ECS
- 정적 에셋은 CDN(Cloudflare R2 + CDN)
- Sentry(에러), Prometheus + Grafana(틱레이트/동접/지연)

### 아트 파이프라인
- Blender 저폴리 모델링 → glb 익스포트
- 캐릭터 **공용 스켈레톤 1개**(장비 교체 위해 필수), 2~5k 트라이앵글
- 애니메이션: Mixamo 리타겟 → idle/walk/run/attack/hit/die
- 초기에는 Kenney(무료 CC0) / Synty 에셋으로 프로토타입 → 이후 자체 제작 교체

## 2. 맵 구조 — 포탈 기반 존(zone)

월드는 하나의 연속된 거대 공간이 아니라 **독립된 맵 여러 개**이고,
플레이어는 포탈을 통과해서 이동한다. 이게 구조 전반에 영향을 준다.

### 결과적으로 얻는 것

- **서버 구조가 단순해진다** — Colyseus 룸 1개 = 존 1개. 존마다 독립 프로세스로 흩어놓기도 쉽다.
- **존 정원이 제한된다** — 존 하나가 감당할 인원의 상한이 명확해져서 용량 계산이 쉽다.
- **에셋 스트리밍이 자연스럽다** — 존 단위로 로드/언로드. 포탈 통과 = 로딩 화면.
  덕분에 초기 로딩에 월드 전체를 받을 필요가 없다.
- **혼잡 해소** — 같은 존의 채널(인스턴스)을 여러 개 띄우면 된다.

### 존 정의 (JSON)

```jsonc
{
  "id": "starter_village",
  "name": "초원 마을",
  "size": 92,               // 한 변 길이. 이동 가능 영역은 size - 8
                            // 화면에 보이는 지면(16:9, 기본 줌)이 약 56.5 사각형이라
                            // 그 1.5배인 84 가 되도록 잡았다
  "spawns": { "default": [0, 0], "from_forest": [40, -12] },
  "portals": [
    {
      "id": "to_forest",
      "position": [42, -8],
      "radius": 2.5,
      "target": { "zone": "dark_forest", "spawn": "from_village" }
    }
  ]
}
```

### 포탈 통과 절차

1. 클라가 포탈 반경 진입 → 서버에 `enterPortal` 요청 (판정은 **서버**가 다시 한다)
2. 서버가 대상 존 룸의 좌석을 예약하고, 캐릭터의 `zoneId`/좌표를 저장
3. 클라는 현재 존을 언로드 → 로딩 화면 → 대상 존 에셋 로드 → 새 룸 접속
4. 대상 존의 지정 스폰 지점에서 재개

**주의**: 존 이동은 "저장 시점"이다. 이동 도중 끊겨도 캐릭터가 사라지지 않게
좌석 예약과 DB 저장 순서를 확실히 잡아야 한다.

## 3. 네트워크 설계 (가장 중요)

```
[클라] 입력(방향/스킬) --20Hz--> [서버] 시뮬레이션 --10~15Hz--> [클라] 스냅샷
```

- **서버 틱 15Hz**, 클라 렌더 60fps
- **클라이언트 예측(prediction)**: 내 캐릭터는 입력 즉시 이동, 서버 스냅샷 오면 보정(reconciliation)
- **보간(interpolation)**: 다른 플레이어는 100~150ms 버퍼 두고 과거 상태 사이를 보간 → 끊김 없음
- **관심영역(AoI)**: Phase 1부터 넣는다. 32m 셀 그리드에서 주변 3x3 셀만 전송.
  해제 반경은 구독 반경보다 한 칸 넓게(히스테리시스) — 같으면 셀 경계에 선 플레이어 주변이 깜빡인다
- **모든 판정은 서버**: 데미지, 쿨타임, 이동속도, 아이템 획득. 클라는 "요청"만 함
- 이동 검증: `이동거리 <= 최대속도 * 경과시간 * 1.1` 초과 시 서버 위치로 강제 스냅

### 공간 그리드를 처음부터 두는 이유

포탈 방식이라 존 인원이 제한되니 전체 브로드캐스트로도 당장은 버틴다.
그런데도 그리드를 Phase 1에 넣는 이유는 **네트워크가 주된 이유가 아니기 때문**이다.

1. **게임플레이가 어차피 공간 질의를 요구한다** — 근접 공격 판정, 광역기 대상 수집,
   몬스터 어그로 범위, 아이템 줍기, 포탈 근접 감지. 전부 매 틱 도는 질의다.
   그리드가 없으면 전부 전체 순회라 존에 100명만 있어도 틱당 수만 번 거리 계산을 한다.
2. **나중에 붙이는 비용은 서버가 아니라 클라이언트에 있다** — 전체 브로드캐스트로 만들면
   클라가 "상태에 있는 엔티티 = 항상 존재"를 전제하게 된다. 뒤늦게 AoI를 넣는 순간
   엔티티가 수시로 생성/소멸하기 시작하고 미니맵·파티원 표시·이름표가 전부 깨진다.
   처음부터 "엔티티는 언제든 나타나고 사라진다"를 전제로 짜면 추가 비용이 거의 없다.

구현: `packages/shared/src/spatialGrid.ts` — 클라(예측용 로컬 질의)와 서버(권위 판정)가 공유한다.
Colyseus 0.16의 `StateView` 로 클라이언트별 상태 필터링에 연결한다.

  앞서는 구간이 없게 했다. 앞서면 경험치 감쇠가 붙어 레벨당 마릿수가 몇 배로 뛴다.
  결과: 레벨당 대체로 4~15마리, **1 → 40 이 약 390마리**.
  `combat.test.ts` 가 총량과 레벨당 상한을 검사하므로 곡선을 건드리면 바로 걸린다.
- [x] 데미지 텍스트 / 몬스터 HP바
- [x] 자동 사냥 — 켠 자리를 앵커로 잡고 반경 22 안의 몬스터를 찾아 접근·공격한다.
  **판단과 이동을 서버가 한다** (`shared/autoHunt.ts` 판단 + `ZoneRoom.driveAutoHunt`).
  클라이언트에서 돌리면 탭을 옮기는 순간 브라우저가 rAF 를 멈추고 타이머를 1Hz 로

## 5. 프로젝트 구조 (모노레포)

```
D:\MMORPG\
├─ packages/
│  ├─ shared/      # 프로토콜 타입, 스탯 공식, 상수, 공간 그리드 (클라·서버 공유)
│  ├─ client/      # Vite + Three.js + React UI
│  └─ server/      # Colyseus + Prisma
├─ assets-src/     # .blend 원본
├─ public/assets/  # 최적화된 .glb/.ktx2
└─ docs/
```
`shared`에 데미지 공식과 이동속도를 두고 클라·서버가 **같은 코드**를 쓰는 게 예측 보정의 핵심.

## 7. 리스크

1. **스코프 폭발** — MMORPG는 개인 프로젝트가 가장 많이 죽는 장르. Phase 3까지가 "게임"이고, 그 이후는 무한 확장. **Phase 0~3을 6개월 안에 못 끝내면 스코프를 줄일 것.**
2. **아트 병목** — 코딩보다 3D 에셋 제작이 더 오래 걸림. 무료 에셋으로 끝까지 가고, 교체는 나중에.
3. **치팅** — 클라이언트를 절대 신뢰하지 않는 구조를 Phase 1부터 지켜야 함. 나중에 고치면 전면 재작성.
4. **서버 비용** — 상시 구동 WebSocket 서버 + DB. 초기 월 $20~50 예상.
