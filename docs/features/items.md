## 규칙

### 생성
- 등급 7개 × 슬롯 6칸 = **42종**. 이름은 `등급 이름 + 슬롯 이름` 이다
  ("일반 무기" … "태초 반지").
- 등급 이름: **일반 · 고급 · 희귀 · 영웅 · 전설 · 초월 · 태초** (`GRADE_NAME`, 2026-09-21 지시).
- id 규칙: `g{등급}_{슬롯코드}` — `g1_w`, `g7_n`. 슬롯코드 `w a h b n r`.
- 착용 레벨은 등급이 정한다: **1 · 31 · 61 · 91 · 121 · 151 · 181** (`gradeLevel`).
- 기본 능력치는 `bonusFor(slot, grade)` = 설계 표 `slotStats(slot, grade)` 를 그대로 담는다.
- **직업별로 나누지 않는다** ★ (2026-09-21 지시: "직업별 장비는 동일해").
  무기도 한 벌이라 `JOB_SLOTS` 는 **빈 표**다. 손에 들리는 모델은 직업이 정하므로
  같은 "전설 무기" 가 법사에게는 지팡이로 보인다.

### 등급 하나로 합쳤다 ★★ (1~7)
- **등급이 곧 성능이다.** 등급 하나 오를 때마다 **×1.7037** (설계의 등비).
  1등급 무기 공 21% → 7등급 514%.
- 등급 하나가 **30레벨을 덮는다.** 그 구간에서 갈아입을 것이 없고, 성장은
  **강화**가 맡는다. 다음 등급을 끼려면 레벨이 30 올라야 한다.
- 나오는 곳은 사냥터가 정한다 (`dropGrades`, 아래 "사냥터가 등급을 정한다").
  7등급은 **마지막 사냥터에서만** 뚫린다.
- 가방 속 `stack.grade` 는 이제 **아이템이 들고 있는 값**이다. 불러올 때
  `getItem(id).grade` 로 다시 맞추므로 id 와 어긋날 수 없다.
- `gradeMultiplier(g) = 1 + (g-1)*0.3` 은 **값(판매가)에만** 쓴다.
- 옛 축의 잔재: `MAX_DROP_GRADE` 는 이제 그냥 7(=전부)이다. 이름만 남았다.

### 랜덤 옵션 ★
- 종류 6개: `crit` 치명타 확률 / `critDamage` 치명타 데미지 / `attackSpeed` 공격 속도 /
  `maxHp` 체력 / `cooldown` 스킬 쿨타임 감소 / `penetration` 방어력 관통.
  **2026-09-20 에 공격력·방어력을 빼고 쿨감·관통을 넣었다** — 공격력·방어력은 슬롯
  기본 수치가 이미 담당하므로 옵션으로 또 주면 "같은 것을 두 번" 이다.
  수치와 개수는 [stat-balance.md](stat-balance.md) 3-2장이 정한다
  (옵션 하나 = DPS +1% 로 값어치를 묶고 종류별 최대치를 역산).
- **옵션도 장비 등급(1~7)을 탄다** ★ — 2026-09-21 까지는 품질 등급(1~10)이라는
  두 번째 축이었는데, 카탈로그를 합치면서 같이 합쳤다. 숨은 축이 하나 더 있으면
  가방에 뜬 숫자가 무엇을 뜻하는지 설명할 수 없다. **같은 등급 안의 편차는 굴림
  자체가 맡는다** — 종류·개수·값이 물건마다 다르다.
- **개수는 전 등급 2개 고정이다** ★ (2026-09-21 지시: "갯수를 항상 2개로 고정").
  등급은 **수치만** 키운다 — 칸마다 줄 수가 같아 물건끼리 비교가 쉽다.
  **종류는 겹치지 않는다.**
- 범위: `optionRange(kind, grade)` = `OPTION_MAX_VALUE[kind] × optionScale(grade)`, 굴림은 그 **50~100%**
  - `optionScale(g) = 0.25 + 0.75*(g-1)/6` → 1등급 25%, 7등급 100%
  - **전부 퍼센트라 레벨을 안 탄다** — 10%는 어디서나 10%다
- **수치는 50배다** ★ (2026-09-21 지시: "지금보다 50배 올려. 예를 들어 치명타 확률이
  40%~75%"). `OPTION_POWER = 50` 한 숫자이고, **반올림 다음에** 곱한다 — 그래야 태초
  치확이 37.5~75 가 아니라 **40~75** 로 떨어진다. 고도는 `balance.json` 의
  `optionPower` 를 읽어 같은 자리에서 곱한다.
  표(`OPTION_MAX_VALUE`)를 직접 안 고친 이유는 "옵션 하나 = DPS +1%" 역산이 살아
  있어야 해서다 — 종류 사이의 비는 그대로고 전체만 커진다.
- **옵션이 커지면서 상한에 쉽게 닿는다.** 판정의 상한은 치확 0.75 · 공속 1.0 ·
  쿨감 0.5 · 관통 0.8 이고(`world.gd` 의 `_refresh_stats`), 태초 치확 옵션 하나가
  40~75%p 라 그것만으로 치확 상한에 닿는다. 균형을 다시 볼 거면 `OPTION_POWER` 와
  이 상한을 같이 본다.
- 저장 형태: `ItemStack.options: { kind, value }[]`. 퍼센트는 **퍼센트 포인트 정수**로
  저장하고, `stackStats` 가 `/100` 해서 비율로 바꾼다. 화면과 판정이 다른 단위를
  쓰면 언젠가 100을 한 번 더 곱하거나 빼먹는다.
- 굴리는 시점(전부 서버): **드롭 · 상점 구입**. 제작을 걷으면서 재굴림은 없어졌다.
- `sanitizeOptions(raw, item, grade)` — 저장값을 지금 규칙으로 다시 자른다.
  종류 중복·범위 초과·없는 종류를 걸러낸다.

### 강화 (+0 ~ +9)
- **기본 수치에 곱한다.** 10단 전체가 **×6** 이고, 뒤로 갈수록 크게 오른다
  (`gear.ts` 의 `enhanceGains` — "첫 구간 : 마지막 = 1 : 7, 전체 곱 = 6").
- **공짜다.** `enhanceCost` 는 0 을 돌려준다 — 아이템 자체가 연료라 골드까지 걸면
  골드를 모으는 일이 된다.
- 성공률은 설계표 그대로 **90% → 10%** 로 내려간다 (`ENH_ODDS`).
- **실패하면 무조건 파괴다. 유지가 없다.** 그래서 같은 등급 여벌이 계속 필요하고,
  사냥터가 아래 등급을 계속 떨구는 이유가 된다.
- 굴림은 서버(`rollEnhance(level, Math.random())`). 클라이언트는 결과만 받는다.

### 능력치 계산
```
baseBonus(item, enhance)        기본(고정) × 강화
stackStats(stack)               기본 + 옵션 → ItemStats
equipmentStats(equipped)        장착 8칸 합
```
`ItemStats = { attack, defense, maxHp, crit, critDamage, attackSpeed }`

장신구(반지·목걸이·귀걸이)와 마법서는 원래 **마나를 주던 자리**였다. 마나를
걷어내면서 그 몫을 공격과 체력으로 옮겼다 — 안 그러면 여덟 자리 중 셋이
빈 물건이 된다.

#### 사냥터가 등급을 정한다 ★★
2026-09-21 요청: **"지금 상태면 1레벨짜리 잡고 최종템을 먹을수도 있는거자나."**

설계에 이미 답이 있었고 **판정이 그걸 안 보고 있었다.** `gear.ts` 의 `dropField(g)` 가
"등급 g 는 어느 사냥터에서 뚫나" 를 정해 둔다 — 2·5·8·11·14·17·20. **착용 레벨보다
한 구간(10레벨) 위**라, 착용 레벨이 돼도 바로는 못 얻고 한 사냥터 더 올라가 이전
등급으로 뚫어야 한다. **그게 상향 압력의 정체다.**

| 사냥터 | 레벨대 | 나오는 등급 |
|---|---|---|
| 1~4 | Lv1~40 | 1 |
| 5~7 | Lv41~70 | 1, **2** |
| 8~10 | Lv71~100 | 2, **3** |
| 11~13 | Lv101~130 | 3, **4** |
| 14~16 | Lv131~160 | 4, **5** |
| 17~19 | Lv161~190 | 5, **6** |
| 20 | Lv191~200 | 6, **7** |

확률은 아래 "드랍 확률은 설계값이다" 를 본다.

- **그 사냥터의 등급과 바로 아래 하나**를 같이 낸다. 하나만 주면 사냥터에 막
  들어선 순간에 아직 쓸 수 없는 등급만 나오고, **강화 여벌**도 끊긴다 —
  강화는 실패하면 파괴라 같은 등급 재고가 계속 필요하다.
- 창 안에서 **아래 등급이 더 흔한 비는 설계가 정한다** (등급별 드랍률의 비).
- 사냥터 1 은 `dropField` 상으로는 아무것도 안 나오는 자리지만(시작 무기를 주므로)
  게임에서는 빈 손이 되므로 1등급을 준다.
- 표는 `gear.ts` 의 `dropGrades(field)` 가 만들고, `npm run export:godot` 이
  `items.json` 의 `dropGrades` 로 내보낸다. **고도는 표만 읽고 역산하지 않는다**
  (`godot/world/items.gd` 의 `drop_grades`).
- **2026-09-21 에 축을 합치면서 이 표가 성능까지 정하게 됐다.** 그 전에는 단계가
  성능을, 등급이 옵션 범위를 맡아 둘이 따로 묶여 있었다. 지금은 사냥터가 정하는
  등급이 **곧 성능**(등비 ×1.7037)이라, Lv1 몬스터가 1등급(공격 21%)만 떨구는 것이
  한 규칙으로 설명된다.

#### 드랍 확률은 설계값이다 ★★
2026-09-21 지적: **"md 파일 준걸로는 1등급 드랍률 0.3% 라고 했는데 지금은 왜 말도 안 되게
높은거지?"**

**한 번도 연결된 적이 없었다.** `DROP_CHANCE = 0.14` 평면값은 설계 문서보다 **먼저**
있던 것(`68b3aef` 고도 이관 2단계)이고, 설계의 `GEAR_DROP_RATE` 는 `balance.json` 의
`gear.dropRate` 로 내보내지기만 할 뿐 **판정에서 아무도 안 읽고 있었다.** 설계
[stat-balance.md](stat-balance.md) 9장의 "코드에 넣을 때 순서" 여섯 단계에 드랍률이
없어서 그 사이로 빠졌다.

- `dropChanceFor(몬스터레벨)` 이 창에 든 등급들의 확률을 **더해서** 돌려준다.
- `rollGrade` 의 등급 비도 설계의 드랍률 비 그대로다. 예전 `2^(n-g)` 는 임의로 반씩
  깎은 값이라 두 표가 어긋났다 — 사냥터 20 은 0.0016 : 0.0011 = **1.45 : 1** 이다.
- **`GEAR_DROP_RATE` 는 퍼센트 단위다.** `0.2963` 은 29.63% 가 아니라 **0.2963%** 다.
  판정에 넣을 때 100 으로 나눈다 (`items.ts` 의 `gearDropRate`, `items.gd` 의
  `grade_drop_rate`). 이걸 한 번 100배로 잘못 읽었다.

| 사냥터 | 나오는 등급 | 킬당 | 몇 마리에 하나 |
|---|---|---|---|
| 1~4 | 1 | 0.2963% | 337 |
| 5~7 | 1 · 2 | 0.2963% · 0.0800% | 266 |
| 8~10 | 2 · 3 | 0.0800% · 0.0321% | 892 |
| 11~13 | 3 · 4 | 0.0321% · 0.0095% | 2,404 |
| 14~16 | 4 · 5 | 0.0095% · 0.0055% | 6,667 |
| 17~19 | 5 · 6 | 0.0055% · 0.0016% | 14,085 |
| 20 | 6 · 7 | 0.0016% · 0.0011% | 37,037 |

**아래 등급이 자기 기준 사냥터를 지나서도 계속 자기 확률로 나오는 것은 의도다** —
강화 여벌이 필요하기 때문이다(실패하면 파괴).

**남은 전제 하나:** 이 값은 "그 사냥터 체류 중에 목표 개수를 채운다" 에서 역산한
것이라 **설계의 사냥 속도**(그룹 50마리를 12~15초)를 가정한다. 지금은 범위 스킬이
4~6마리만 쳐서 그 속도가 안 나오므로, 체감은 설계보다 야박하다. 스킬 계수(설계 5장)가
정해지면 킬 속도가 올라오면서 저절로 맞는다 — **드랍률을 다시 만질 일이 아니다.**

- **2026-09-21: 카탈로그를 붙였다.** 단계 20개 축이 사라지고 **등급 7개가 유일한

남은 것은 **보스 드롭**뿐이다 — 보스는 아직 금화만 준다.

|---|---|---|
| 축 | 단계 20개(요구 레벨) × 등급 1~10 | **등급 7개**뿐 |
| 수치 | 단계를 연속 등급으로 보간 | **설계표 칸 그대로** |
| 등급이 하는 일 | 랜덤 옵션 범위만 넓힌다 | **성능 그 자체** (등비 ×1.7037) |
| 강화 | ×1+0.08n, 파괴는 +7부터 | 10단계 총 **×6**, 실패하면 **무조건 파괴** |
| 종수 | 160 (무기 직업 3벌) | **42** (전 직업 공용) |

**42종인 이유는 아이템 레벨 축을 없앴기 때문**이다. 등급 하나가 30레벨을 덮으므로
그 안에서는 갈아입을 것이 없고, 대신 **강화**와 **다음 등급 착용 레벨**이 성장을 맡는다.

### 옛 저장은 자리를 맞춰 옮긴다

id 가 전부 바뀌었으므로(`w_fighter_07` → `g3_w`) 그냥 두면 저장된 가방이 통째로
빈다. `migrateItemId`(고도는 `Items.migrate_id`)가 **단계 → 요구 레벨 → 등급**으로
옮겨 준다. 제작 재료(`m_XX`)는 갈 자리가 없어 버린다. **옛 저장이 다 지나가면
지워도 되는 다리다.**

### 장신구를 무기·갑옷의 절반으로 ★★ (2026-09-21)

지시: "목걸이랑 반지에 공격력 방어력 hp를 넣고 치명타랑 공속 옵션은 제거하자.
대신 공격력 방어력 hp를 무기랑 방어구의 수치 반만 넣어."

- **장비 기본 수치는 공격·방어·HP 셋뿐이다.** 치확·치피·공속은 **랜덤 옵션 전담**이
  됐다 — 목걸이의 치확 50%p, 반지의 공속 20% 가 사라졌다.
- **목걸이·반지 = 무기·갑옷의 정확히 절반.** 지분이 공격 0.5 : 0.25 : 0.25,
  방어·HP 가 갑옷 1/3 : 나머지 네 칸 1/6 씩이다.
- **풀세트 총합은 그대로다.** 열 합계 100% 를 지켜야 설계 예산(`gradeSum`)이 맞으므로
  장신구가 올라간 만큼 무기(60→50%)·갑옷(40→33%)이 내려갔다. 장신구만 올리면
  풀세트가 예산의 120% 가 되어 몬스터 HP·체류 킬 수가 전부 어긋난다.
- **딸려 온 것: 몬스터 HP 가 내려갔다.** 기준 플레이어의 평균 피해 배수
  (`1 + 치확 × 치피`)가 사라져서다 — Lv200 몬스터 60,224 → **41,801**(-30%),
  레벨당 킬 수도 같이 줄었다. **동레벨 6타·만렙 2,880시간은 그대로다.**
  → [stat-balance.md](stat-balance.md) 3·6·7장을 같이 고쳤다.

### 어떻게 만들었나

식을 새로 짓지 않았다. `tools/balance_sim.py` 의 함수를 이름까지 그대로 옮기고,
**두 구현이 같은 값을 내는지 대조**한 뒤 그 식으로 56종을 생성했다.

```
풀셋 합(g)   = 35 × 1.7037^(g-1)              → 35 … 856
예산         = 공격 합 × 1.0 / 방어 × 0.6 / HP × 0.35
슬롯 수치    = 예산 × 슬롯 지분 × 강화배수     ← 강화는 공/방/HP 에만
치확·공속    = 최대치 × (g-1)/6                ← 등급에 선형, 강화 안 먹음
```

- **슬롯 지분**은 설계 문서의 "슬롯 6개" 표(무기 공격 60%, 갑옷 방어·HP 40% …)이고,
  스탯마다 열 합계가 정확히 100% 라 **풀세트를 맞추면 예산이 딱 떨어진다.**
- **강화 증가율**은 닫힌 식이 없다. "첫 구간 : 마지막 = 1 : 7, 전체 곱 = 6" 을
  만족하는 첫 구간 값을 이분법으로 찾는다 — 시뮬레이터와 같은 방법이라 같은 값이 나온다.
- **드랍률**(`GEAR_DROP_RATE`)만은 식이 아니라 박아 둔 값이다. 체류 킬 수에서
  역산하는 값이라 성장 곡선까지 들고 와야 해서, `--drops` 출력을 옮기고 주석에
  출처를 적었다.

`gear.test.ts` 는 **설계 문서의 숫자를 손으로 박아 두고** 대조한다 — 식에서 다시
계산해 비교하면 식이 틀려도 통과하므로 의미가 없다.

## 손댈 때

- 수치 균형을 만질 거면 `optionScale` 하나만 건드려도 옵션 전체가 같이 움직인다.
- 옵션 종류를 추가하면: `OptionKind` → `OPTION_KINDS` → `OPTION_LABEL` →
  `OPTION_MAX_VALUE` → `stackStats` 의 switch → (능력치면) `ItemStats` 와
  `ZoneRoom.statsOf` → 전투에서 소비하는 자리. 여섯 군데다.
- **아이콘은 슬롯당 한 장**이다. 등급이 보이게 하려면 칸 테두리 색이나 배지로
  하는 쪽이 싸다 — 42장을 굽는 것보다.
- 저장 형식을 바꾸면 `db.ts` 의 `toStack`/`withOptions` 를 반드시 같이 고친다.
  **기존 캐릭터의 가방을 깨뜨리면 안 된다.**
