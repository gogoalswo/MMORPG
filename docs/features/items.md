## 규칙

### 생성
- 단계 20개, 접두어 표(`TIER_PREFIX`: 낡은 → … → 종말).
- `tierLevel(i)` = 0단계는 1, 나머지는 `i * 10`.
- 단계마다 슬롯 6종. 무기만 직업 3벌 → 단계당 5 + 3 = 8개 × 20 = **160개**다.
  (기사를 지우고 보조·귀걸이를 없애며 280 → 240 → 180, 제작 재료 20종을 걷으며 160.)
- id 규칙: `{슬롯코드}_{직업}_{단계2자리}` 또는 `{슬롯코드}_{단계2자리}`.
  슬롯코드 `w o a h b r n e`.
- 기본 능력치는 `bonusFor(slot, level, job)` — 슬롯 성격별 가중치
  (갑옷 > 투구 > 신발 = 1 : 0.6 : 0.45).

### 등급 (1~10)
- **드롭은 7등급까지**(`MAX_DROP_GRADE = GRADE_COUNT`). 제작을 걷으며 잠깐 10 이었다가
  **2026-09-21 에 7로 되돌렸다** — 사냥터별 상한을 걸면서 "길이 끊긴다"는 이유가
  사라졌고, 8~10 은 설계에 근거가 없는 숫자였다. 품질 등급 축(1~10)은 옵션 개수·범위에
  그대로 남아 있고, 드롭이 내는 범위만 7까지다.
- 드롭 등급 비: 창 안에서 **설계의 드랍률 비 그대로** (아래 "사냥터가 등급을 정한다").
- **등급은 기본 수치에 곱하지 않는다.** (예전에는 곱했다. 바뀌었다.)
  지금 등급이 하는 일은 **옵션 범위를 넓히는 것**뿐이다.
- `gradeMultiplier(g) = 1 + (g-1)*0.3` 은 이제 **값(판매가)에만** 쓴다.

### 랜덤 옵션 ★
- 종류 6개: `crit` 치명타 확률 / `critDamage` 치명타 데미지 / `attackSpeed` 공격 속도 /
  `maxHp` 체력 / `cooldown` 스킬 쿨타임 감소 / `penetration` 방어력 관통.
  **2026-09-20 에 공격력·방어력을 빼고 쿨감·관통을 넣었다** — 공격력·방어력은 슬롯
  기본 수치가 이미 담당하므로 옵션으로 또 주면 "같은 것을 두 번" 이다.
  수치와 개수는 [stat-balance.md](stat-balance.md) 3-2장이 정한다
  (옵션 하나 = DPS +1% 로 값어치를 묶고 종류별 최대치를 역산).
- **개수는 품질 등급이 정한다** — 1등급 1개 → 10등급 4개. **종류는 겹치지 않는다.**
- 범위: `optionRange(kind, grade, level)` = `baseOptionRange(kind, level) × optionGradeScale(grade)`
  - `optionGradeScale(g) = 1 + (g-1)*0.35` → 1등급 1.0, 10등급 4.15
  - 퍼센트 옵션(치명타/공속/치명타데미지)은 **레벨을 안 탄다** — 10%는 어디서나 10%
  - 수치 옵션은 요구 레벨을 탄다. 안 그러면 200레벨 장비의 공격력 +3은 붙으나 마나
  - 1등급 최대가 그 자리 기본의 3할쯤, 10등급 최대가 기본을 조금 넘는 선으로 잡았다
- 저장 형태: `ItemStack.options: { kind, value }[]`. 퍼센트는 **퍼센트 포인트 정수**로
  저장하고, `stackStats` 가 `/100` 해서 비율로 바꾼다. 화면과 판정이 다른 단위를
  쓰면 언젠가 100을 한 번 더 곱하거나 빼먹는다.
- 굴리는 시점(전부 서버): **드롭 · 상점 구입 · 새로 만들기 · 등급 올리기(재굴림)**.
  등급을 올리면 범위가 넓어지므로 다시 굴린다. 안 그러면 10등급인데 1등급 범위
  옵션이 박힌 물건이 남는다.
- `sanitizeOptions(raw, item, grade)` — 저장값을 지금 규칙으로 다시 자른다.
  종류 중복·범위 초과·없는 종류를 걸러낸다.

### 강화 (+0 ~ +10)
- **기본 수치에 곱한다**: `enhanceMultiplier(n) = 1 + n*0.08`.
- 골드만 쓴다: `enhanceCost(item, n) = round(item.price * 2 * (n+1))`.
- 확률(`enhanceOdds`):

  | 구간 | 성공 | 유지 | 파괴 |
  |---|---|---|---|
  | +0~3 | 95% | 5% | 0% |
  | +4~6 | 70% | 30% | 0% |
  | +7~8 | 45% | 45% | 10% |
  | +9~10 | 30% | 50% | 20% |

- 파괴되면 아이템이 가방에서 사라진다. **골드는 결과와 무관하게 항상 소비**된다.
- 굴림은 서버(`rollEnhance(level, Math.random())`). 클라이언트는 결과만 받는다.

### 능력치 계산
```
baseBonus(item, enhance)        기본(고정) × 강화
stackStats(stack)               기본 + 옵션 → ItemStats
equipmentStats(equipped)        장착 8칸 합
```
`ItemStats = { attack, defense, maxHp, crit, critDamage, attackSpeed }`

장신구(반지·목걸이·귀걸이)와 마법서는 원래 **마나를 주던 자리**였다. 마나를
걷어내면서 그 몫을 공격과 체력으로 옮겼다 — 안 그러면 여덟 자리 중 셋이
빈 물건이 된다.

#### 사냥터가 등급을 정한다 ★★
2026-09-21 요청: **"지금 상태면 1레벨짜리 잡고 최종템을 먹을수도 있는거자나."**

설계에 이미 답이 있었고 **판정이 그걸 안 보고 있었다.** `gear.ts` 의 `dropField(g)` 가
"등급 g 는 어느 사냥터에서 뚫나" 를 정해 둔다 — 2·5·8·11·14·17·20. **착용 레벨보다
한 구간(10레벨) 위**라, 착용 레벨이 돼도 바로는 못 얻고 한 사냥터 더 올라가 이전
등급으로 뚫어야 한다. **그게 상향 압력의 정체다.**

| 사냥터 | 레벨대 | 나오는 등급 |
|---|---|---|
| 1~4 | Lv1~40 | 1 |
| 5~7 | Lv41~70 | 1, **2** |
| 8~10 | Lv71~100 | 2, **3** |
| 11~13 | Lv101~130 | 3, **4** |
| 14~16 | Lv131~160 | 4, **5** |
| 17~19 | Lv161~190 | 5, **6** |
| 20 | Lv191~200 | 6, **7** |

확률은 아래 "드랍 확률은 설계값이다" 를 본다.

- **그 사냥터의 등급과 바로 아래 하나**를 같이 낸다. 하나만 주면 사냥터에 막
  들어선 순간에 아직 쓸 수 없는 등급만 나오고, **강화 여벌**도 끊긴다 —
  강화는 실패하면 파괴라 같은 등급 재고가 계속 필요하다.
- 창 안에서 **아래 등급이 더 흔한 비는 설계가 정한다** (등급별 드랍률의 비).
- 사냥터 1 은 `dropField` 상으로는 아무것도 안 나오는 자리지만(시작 무기를 주므로)
  게임에서는 빈 손이 되므로 1등급을 준다.
- 표는 `gear.ts` 의 `dropGrades(field)` 가 만들고, `npm run export:godot` 이
  `items.json` 의 `dropGrades` 로 내보낸다. **고도는 표만 읽고 역산하지 않는다**
  (`godot/world/items.gd` 의 `drop_grades`).
- **성능(단계)은 원래부터 묶여 있었다.** `tierForLevel(몬스터레벨) = floor(L/10)` 이라
  Lv1 몬스터는 단계 0(낡은 너클, 공격 21)만 떨군다. 새로 묶은 것은 **품질 등급**이고,
  지금은 옵션 범위만 넓히지만 카탈로그를 56종으로 갈면 **등급이 곧 성능**(등비 ×1.7037)이
  되므로 그때를 위해서도 필요하다.

#### 드랍 확률은 설계값이다 ★★
2026-09-21 지적: **"md 파일 준걸로는 1등급 드랍률 0.3% 라고 했는데 지금은 왜 말도 안 되게
높은거지?"**

**한 번도 연결된 적이 없었다.** `DROP_CHANCE = 0.14` 평면값은 설계 문서보다 **먼저**
있던 것(`68b3aef` 고도 이관 2단계)이고, 설계의 `GEAR_DROP_RATE` 는 `balance.json` 의
`gear.dropRate` 로 내보내지기만 할 뿐 **판정에서 아무도 안 읽고 있었다.** 설계
[stat-balance.md](stat-balance.md) 9장의 "코드에 넣을 때 순서" 여섯 단계에 드랍률이
없어서 그 사이로 빠졌다.

- `dropChanceFor(몬스터레벨)` 이 창에 든 등급들의 확률을 **더해서** 돌려준다.
- `rollGrade` 의 등급 비도 설계의 드랍률 비 그대로다. 예전 `2^(n-g)` 는 임의로 반씩

  판정에 넣을 때 100 으로 나눈다 (`items.ts` 의 `gearDropRate`, `items.gd` 의

**남은 전제 하나:** 이 값은 "그 사냥터 체류 중에 목표 개수를 채운다" 에서 역산한

정해지면 킬 속도가 올라오면서 저절로 맞는다 — **드랍률을 다시 만질 일이 아니다.**

### 무엇이 다른가

| | `items.ts` (지금) | `gear.ts` (설계) |
|---|---|---|
| 축 | 단계 20개(요구 레벨) × 등급 1~10 | **등급 7개**뿐 |
| 수치 | 절대값 (`공격 = 2 + 레벨×0.6`) | **기본 스탯의 %** |
| 등급이 하는 일 | 랜덤 옵션 범위만 넓힌다 | **성능 그 자체** (등비 ×1.7037) |
| 강화 | +0~+10, ×1+0.08n, 파괴는 +7부터 | 10단계, 총 **×6**, 실패하면 **무조건 파괴** |
| 종수 | 160 | **56** |

**56종인 이유는 아이템 레벨 축을 없앴기 때문**이다. 등급 하나가 30레벨을 덮으므로
그 안에서는 갈아입을 것이 없고, 대신 **강화**와 **다음 등급 착용 레벨**이 성장을 맡는다.
7 × (무기 3직업 + 나머지 5칸) = 56.

### 어떻게 만들었나

식을 새로 짓지 않았다. `tools/balance_sim.py` 의 함수를 이름까지 그대로 옮기고,
**두 구현이 같은 값을 내는지 대조**한 뒤 그 식으로 56종을 생성했다.

```
풀셋 합(g)   = 35 × 1.7037^(g-1)              → 35 … 856
예산         = 공격 합 × 1.0 / 방어 × 0.6 / HP × 0.35
슬롯 수치    = 예산 × 슬롯 지분 × 강화배수     ← 강화는 공/방/HP 에만
치확·공속    = 최대치 × (g-1)/6                ← 등급에 선형, 강화 안 먹음
```

- **슬롯 지분**은 설계 문서의 "슬롯 6개" 표(무기 공격 60%, 갑옷 방어·HP 40% …)이고,
  스탯마다 열 합계가 정확히 100% 라 **풀세트를 맞추면 예산이 딱 떨어진다.**
- **강화 증가율**은 닫힌 식이 없다. "첫 구간 : 마지막 = 1 : 7, 전체 곱 = 6" 을
  만족하는 첫 구간 값을 이분법으로 찾는다 — 시뮬레이터와 같은 방법이라 같은 값이 나온다.
- **드랍률**(`GEAR_DROP_RATE`)만은 식이 아니라 박아 둔 값이다. 체류 킬 수에서
  역산하는 값이라 성장 곡선까지 들고 와야 해서, `--drops` 출력을 옮기고 주석에
  출처를 적었다.

`gear.test.ts` 는 **설계 문서의 숫자를 손으로 박아 두고** 대조한다 — 식에서 다시
계산해 비교하면 식이 틀려도 통과하므로 의미가 없다.
