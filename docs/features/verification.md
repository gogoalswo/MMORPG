# 검증 방법

## 원칙

**글로 확인한다. 스크린샷은 정말 눈으로 봐야 할 때 한 장만.**

이유가 둘이다.

1. **비용** — 스크린샷 한 장이 토큰 천 단위다. 같은 확인을 텍스트로 하면 수십 단위다.
2. **정확도** — 브라우저 창이 가려지면 `requestAnimationFrame` 이 0~1Hz 로 떨어진다.
   화면은 낡은 채로 굳고, 그 좌표를 보고 클릭하면 엉뚱한 자리를 누른다.
   실제로 이것 때문에 같은 검증을 여섯 번 반복하고 "버그다"라고 오진한 적이 있다.
   서버 상태와 DOM 은 그런 것과 무관하게 항상 지금 값이다.

**남긴다.** 확인한 내용은 `logs/` 아래 파일로 남는다. 나중에 "그때 뭐가 나왔더라"를
다시 굴려보지 않아도 되게.

## 도구

| 도구 | 무엇을 보나 |
|---|---|
| `npm run probe -- <명령>` (`scripts/probe.mjs`) | **서버 로직** — 접속해서 상태·전투·아이템·메시지를 글로 찍는다 |
| `scripts/ui-probe.js` | **클라이언트 UI** — DOM 을 글로 뽑는 조각 모음 (콘솔에 붙여 넣는 용도) |
| 화면 왼쪽 스킬 목록 | **장착 없이 스킬을 쏜다** — 이펙트를 볼 때 스킬창을 오갈 필요가 없다 (옛 client-ui.md(지워짐)) |
| `npm run probe -- state` | 배운 스킬·액션바·포인트도 같이 찍는다 (`[스킬]` 줄) |
| `npm run probe -- god` | **무적 모드** — 켜고 맞아 보면서 체력이 안 깎이는지, 그래도 `hit` 은 오는지 ([combat.md](combat.md)) |
| `npm run probe -- root` | **공격 경직** — 사람은 걸으면서 공격을 끼워, 몬스터는 맞은 직후 도망치며 구간별 이동 거리를 잰다 ([combat.md](combat.md)) |
| `scripts/probe.mjs walk` | **충돌** — 몬스터에게 걸어가 멈추는 거리를 찍는다. `--player` 면 다른 캐릭터에게. 끝에 **겹침 검사**(몬스터끼리) ([collision.md](collision.md)) |
| `scripts/fx-probe.ts` | **스킬 이펙트** — 브라우저 없이 돌려 자리·크기·방향·밝기를 글로 찍는다 |
| `scripts/hit-probe.ts` (`npm run hit-probe`) | **클릭 표적** — 몬스터를 몇 픽셀 안에서 누를 수 있는지, 앞줄이 뒷줄을 몇 % 가리는지 |
| `logs/server.log` | 서버 출력. `npm run server` 와 `npm run dev` 의 자동 실행이 남긴다 |
| `scripts/db-peek.mjs` | 저장된 캐릭터를 훑는다 |
| `scripts/edit.mjs` | **파일 고치기** — 개행(CRLF/LF)을 묻지 않고 부분 치환한다. `grep` 은 이 저장소의 개행을 판정하지 못한다 (CLAUDE.md) |
| `npm test` | 데이터 규칙 전수 검사 |
| `__localServer` (콘솔) | **로컬 모드**의 서버 상태 — 룸·플레이어·몬스터를 글로 (옛 local-mode.md(지워짐)) |

## 헤드리스 클라이언트 (`probe.mjs`)

화면 없이 진짜로 접속한다. 캐릭터가 없으면 사람과 같은 순서로 만들고 고른다 —
서버에 검증용 예외 경로를 뚫지 않는다.

```bash
npm run probe -- state --zone meadow            # 내 상태 / 가방 / 장비 / 주변 몬스터 / 몬스터끼리 겹침
npm run probe -- fight --rounds 3 --zone meadow # 지목 + 자동 사냥으로 싸우며 타격·치명타 집계
npm run probe -- aim --zone meadow              # 클릭 타겟팅 — 제자리인지, 각이 도는지, 사거리 밖이면 안 맞는지, 안 찍고 쏘면 가까운 놈이 맞는지
npm run probe -- send npcBuy w_archer_06        # 아무 메시지나 보내고 결과를 본다
npm run probe -- watch --seconds 20             # 상태 변화를 지켜본다
npm run probe -- walk --player --zone meadow    # 캐릭터끼리 충돌 — watch 로 하나 세워 두고 걸어간다
npm run probe -- root --zone meadow             # 공격 경직 — 휘두르는 동안 이동이 막히는지
npm run probe -- god --zone meadow              # 무적 모드 — 안 깎이는지, 그래도 맞은 건 오는지
```

실제 출력 (`god` — 무적 모드):
```
무적 상태: 켜짐
무적 켜고 4초: 체력 -0 (0 이어야 한다) · 맞은 횟수 4 (0 이면 공격 동작이 안 돈다)
  그중 피해 0 으로 온 것 4회 (맞은 횟수와 같아야 한다)
끈 뒤 상태: 꺼짐
무적 끄고 4초: 체력 -32 (0 이면 안 된다) · 맞은 횟수 4
```
- **맞은 횟수가 0 이 되면 실패다.** 몬스터 공격 동작은 `hit` 으로 도는데, 무적이
  그 메시지까지 막으면 동작을 보려고 켠 무적이 동작을 못 보게 만든다.
- **무적 켠 구간을 먼저 잰다.** ★ 끄고 먼저 재면 1레벨이 4초를 못 버티고 쓰러지는데,
  죽은 뒤에는 `damagePlayer` 가 `dead` 로 바로 빠져나가 체력 -0 · 맞은 횟수 0 이
  나온다 — **무적이라서 안 깎인 건지 죽어서 안 맞는 건지 구분이 안 되는 거짓 결과다.**
  실제로 이 순서 때문에 멀쩡한 무적을 고장 났다고 읽은 적이 있다.
- 기본 이름은 `검증` 뒤에 꼬리가 붙는다. 매번 게스트 계정이 새로 생기는데 이름은
  서버 전체에서 하나뿐이라, 고정 이름이면 두 번째 실행부터 "이미 사용 중"으로 막힌다.

실제 출력 (`root` — 공격 경직, 사람과 몬스터를 한 번에):
```
대상 mob003 21.5m · 옆으로 걷는다
  공격 전 0.4초: 1.84m (RUN_SPEED 4.6 이면 1.8m 쯤)
  공격 직후 0.4초: 0.00m (경직 중이라 0 에 가까워야 한다)
  그 다음 0.4초: 1.84m (경직이 풀려 다시 걸어야 한다)
--- 몬스터 경직: mob003 에게 붙어서 한 대 맞아 본다 ---
  맞은 직후 0.4초 몬스터 이동: 0.00m (경직 중이라 0 에 가까워야 한다)
  그 다음 0.4초 몬스터 이동: 1.41m (쫓아온다 — moveSpeed 3.6 × 0.4)
```
- **대상 옆을 스쳐 가는 방향으로 걷는다.** 대상에게 박혀 서면 안 움직인 것이
  충돌 때문인지 경직 때문인지 구분이 안 된다.
- **몬스터 쪽은 맞은 직후에 도망치면서 잰다.** 가만히 서서 재면 몬스터도 때리느라
  서 있어서 경직이 있으나 없으나 0 이 나온다.
- **경직 길이도 잰다** (마지막 두 줄). 5cm 넘게 움직인 첫 순간을 찾는 방식이라
  서버 틱과 상태 전송 간격만큼(0.1~0.2초) 길게 나온다 — 0.4초가 0.49초, 0.65초가
  0.81초로 잡힌다. 늘어난 폭이 그보다 크면 경직 값이 실제로 달라진 것이다.
- 여기서 안 잡히는 것: **공격 클립을 어떻게 트는지는 화면에서만 일어난다.** 짐승은
  긴 클립에서 경직과 같은 길이의 창만 잘라 트는데, 그 창이 어긋나면 이 probe 는
  그대로 통과한다 → [characters-and-animation.md](characters-and-animation.md) 의
  "공격 클립과 이동".

옵션: `--zone --token --character --name --job --server --rounds --seconds --log --quiet`

- 토큰 없이 돌리면 **게스트로 새 캐릭터**를 만든다. 깨끗한 상태에서 보고 싶을 때 좋다.
- 기존 캐릭터로 보려면 `--token`(브라우저 `localStorage['mmo:token']`)과 `--character` 를 준다.
  **토큰은 자격증명이다. 저장소에 커밋하지 않는다.**
- 결과는 `logs/probe-<명령>-<시각>.log` 로 남는다.

실제 출력 (지목 + 자동 사냥 + 치명타 확인):
```
--- 1회차: mob003 hp 100, 21.8m ---
[대상] 3aa7b06d-...
  거리 20.7m 대상 hp 100 내 hp 100
  거리 8.4m  대상 hp 58  내 hp 100
[처치] 3aa7b06d 마지막 28
[보상] 들늑대 +31 exp
타격 24회 · 치명타 3회 (12.5%) · 누적 피해 437
```

실제 출력 (`aim` — 클릭 타겟팅):
```
지목: mob003 hp 100/100 · 거리 21.2m
  지목 1.5초 뒤 내가 움직인 거리 0.00m (제자리여야 한다)
  걸어서 7.8m 까지 붙었다 — 여기서부터는 안 움직여야 한다
  쏘기 전 내 rotY -2.38 / 대상 방향 -2.38
  기본 공격 뒤 rotY -2.38 (대상 방향 -2.38) · 대상 hp 100 → 86
  piercing_shot: 대상 hp 86 → 58 · 거리 2.1m
먼 놈 지목: mob008 47.9m — 사거리 밖이라 안 맞아야 한다
  타격 0회 (0 이어야 한다) · 내가 움직인 거리 0.00m
[대상] 해제
지목 없이 스킬 — 가장 가까운 mob008 (1.9m) 가 맞아야 한다
[대상] d4c44534-03aa-465e-bad5-10c2874d473a
  mob008 hp 67 → 41 (줄어야 한다)
```
- **`aim` 은 지목이 이동을 시키지 않는지부터 본다.** 예전 클릭 추격이 여기서
  달려갔다 — 되돌아가는 변경이 있으면 이 줄이 먼저 깨진다.
- 사거리 안까지는 `input` 으로 직접 걸어간다. 8m 를 고른 이유는 원거리 스킬
  (사거리 11~14)에는 들어오고 근접 판정에는 절대 안 닿아, **타겟 자리에서 터진
  것인지 구분이 되기 때문**이다.
- 마지막 절은 **조준을 풀고 스킬만 누른다.** 서버가 사거리 안 가장 가까운 놈을
  잡아 `[대상] <id>` 로 알려주고 그놈의 hp 가 줄어야 한다
  ([auto-hunt-and-targeting.md](auto-hunt-and-targeting.md) 의 "안 찍고 스킬을
  누르면"). `[대상]` 줄이 없으면 서버가 옛 코드로 떠 있는 것이다.

## UI 확인 (`ui-probe.js`)

`javascript_tool` / 브라우저 콘솔에 **함수 본문을 골라 붙여 넣는다.** 들어 있는 것:

- `summary()` — 존, HP, 열린 창, 말걸기 프롬프트, 자동사냥 상태, 물고 있는 대상, 최근 채팅
- `bag()` — 골드, 칸 수, 장비 툴팁, 각 칸 이름, 상세, 옵션 칩과 범위
- `npc()` — NPC 창 섹션과 줄 전부
- `layout()` — 각 요소의 위치·`pointer-events`·화면 밖 여부 (모바일 확인용)
- `hitTest(sel)` — 그 자리를 누르면 정말 그게 눌리는지
- `tap(sel)` — 손가락 탭을 흉내내 실제 히트 테스트를 거쳐 누른다

주의: **rAF 로만 갱신되는 값**(이름표 화면 좌표, 쿨타임 표시, 말걸기 프롬프트)은
창이 가려져 있으면 낡은 값이다. 그것들을 봐야 하면 창을 앞으로 꺼낸 뒤
**같은 호출 안에서** 읽는다.

## 고도 이펙트는 찍어서 본다 (`npm run shot:godot`) ★

**이펙트만은 글로 확인이 안 된다** (2026-09-18). 낙뢰를 노드 수치로만 확인하고
"됐다" 고 했다가 **"퀄리티가 너무 떨어진다"** 는 지적을 받았다. 테스트는 전부
통과였다 — 방출기 21개, 알갱이 99개, 줄기 338px, 뒤에서 앞으로 36°.
화면에는 이랬다:

- **번개가 없었다.** 2.6m 짜리 가닥을 초속 62m 로 날렸더니 8.6m 를 0.14초에
  지나가 프레임 사이로 사라졌다. 노드로는 "섰다" 가 맞다
- 땅의 금은 **흰 꽃**이었다 (청백색 가산 혼합 열둘이 고르게 방사)
- 파편은 **노란 알갱이 무리**였다 (흙빛인데 가산 혼합이라 빛났다)
- 섬광은 **흰 육각형**이었다 (`radial_segments = 6`)

고치는 데 쓴 것이 이 명령이다. 가상 디스플레이(`xvfb`)에 게임을 띄워
**Compatibility(OpenGL)** 로 굽고 — 웹 익스포트와 같은 렌더러다 — 스킬을 한 번
시전해 `logs/shot_NN.png` 로 뽑는다.

```bash
npm run shot:godot                   # 낙뢰(thunder_fall)
npm run shot:godot -- rising_kick    # 스킬 id 를 주면 그것
npm run shot:godot -- kill           # 가까운 몬스터를 한 대에 잡는다 — 피해 숫자·왼쪽 아래 채팅창
npm run shot:godot -- sky_breaker 8,27,54,108,243,432   # 찍을 프레임을 준다 (긴 이펙트)
npm run shot:godot -- rising_kick@225 # @각도(도, 0 = +Z) — 그 쪽을 보고 쓴다. 캐릭터 기준 이펙트는
                                      # 보는 쪽마다 화면 모양이 달라 두세 방향을 찍어 본다 (225 = 화면 위)
npm run shot:godot -- portal         # 차원문 소용돌이 (스킬이 아니라 늘 켜진 이펙트)
npm run shot:godot -- gate           # 차원문 창 (logs/gate_off.png · gate_on.png=줄 누른 채)
npm run shot:godot -- range:tiger_roar   # 스킬 범위 표시 (logs/range_NN.png)
```

- **`--headless` 로는 아무것도 안 그려진다.** 헤드리스는 더미 렌더러라 화면이
  검게 나온다. `xvfb-run` + `--rendering-driver opengl3` 이어야 한다
  (Vulkan/mobile 은 소프트웨어 GL 에서 안 뜬다).
- **시간을 늦춰서 찍는다** (`shot.gd` 의 `SLOW` 0.08). 소프트웨어 렌더가 5~9fps 라
  프레임 간격이 0.1~0.2초인데 이펙트 한 토막은 0.12초짜리다 — 제 속도로 찍으면
  이미 꺼진 뒤만 남는다. **처음에 번개를 못 본 것도 이 때문이었다.**
- 한 번 돌리면 **여섯 장**과, 그 가운데를 잘라 3열로 붙인 **`logs/shot_sheet.png`**
  한 장이 나온다. ★ **시간 순서는 이 한 장으로 본다** — 여섯 장을 따로 읽으면
  여섯 배를 낸다 (2026-09-23 천붕각부터).
- **찍힌 시각은 출력의 "게임 시간" 을 믿는다.** 예전에는 프레임 × 0.15 × `SLOW` 로
  어림해 "0.36초쯤" 이라 적었는데, 재 보니 기본 여섯 장은 **실제로는 0.1초 남짓**
  까지다 (150프레임이 0.56초). 1초가 넘는 이펙트(천붕각 2초)는 **둘째 인자로
  프레임을 준다** — 0.05~1.5초면 `8,27,54,108,243,432`.
- **`range:<스킬id>` 는 사냥터로 간다.** ★ 스킬 범위 표시(`SkillRange`)를 보는
  모드다. 마을에서 찍으면 모양은 나오지만 **덮는 넓이**를 못 본다 — 범위기를
  보는 이유가 그건데. 그래서 초원의 무리 한가운데(-28, -28)에 세우고 찍는다
  (`shot.gd` 의 `RANGE_*`). 반경·각이 판정과 같은지는 `skill_test.gd` 가 숫자로
  보고, 여기서는 **50마리 사이에서 얼마나 덮나**만 본다 → [skills.md](skills.md)
- **`portal` 은 다른 길로 간다.** 시전할 스킬이 없고 늘 돌아가는 이펙트라,
  시간을 늦추지 않고 문 앞(6m)에 세운 뒤 네 장을 찍는다. 이때 **게임의
  `_process` 를 끈다** — 안 끄면 카메라가 매 프레임 캐릭터를 다시 쫓아가 문이
  화면 구석으로 밀린다. 카메라는 게임과 같은 각(요 45·피치 42)으로 두고 거리만
  9m 로 당긴다 (`shot.gd` 의 `PORTAL_*`).
- **에셋이 없어도 된다.** 캐릭터는 기둥, 바닥은 회색이지만 이펙트는 코드로 짓는
  것이라 그대로 보인다. 다만 **밝은 바닥에서는 가산 혼합이 흰색으로 날아간다** —
  색이 옅으면 실제 사냥터(초원·돌)보다 하얗게 보이니 색 판단은 조금 깎아서 한다.
- 노드 수치 테스트(`*_fx_test.gd`)를 대신하는 게 아니다. **자리·크기·타이밍은
  테스트가, 생김새는 이 그림이** 본다. 테스트가 통과인데 화면이 이상한 경우가
  실제로 있었으니 둘 다 본다.

### 두 번째 시전을 찍는다 (2026-09-23)

이펙트는 풀(`FxPool`)에서 되감아 쓰므로 `shot.gd` 는 스킬을 **한 번 제 속도로 다
돌린 뒤 두 번째를 찍는다.** 한 번 끝난 것이 제대로 되감기는지(꺼 둔 줄기가 다시
켜지나, 방출기가 다시 터지나)가 첫 시전보다 잘 깨지는 자리다.

## 히치는 덩어리별로 잰다 (`godot/tools/hitch.gd`) ★

```
godot --headless --path godot --script tools/hitch.gd
```

사냥터 무리 한가운데서 스킬마다 네 번 쓰고, 한 프레임을 **시전 판정 · 판정 틱 ·
이벤트별 그리기 · 화면 틱**으로 나눠 가장 긴 값을 찍는다. 맨 아래 `(안 씀)` 줄이
스킬 없이 서 있을 때의 바닥값이다. 프레임 전체만 재면 무리 속 몬스터 틱이
들쭉날쭉해서 스킬 몫이 묻힌다 — 그래서 전송과 `game._process` 를 멈추고 직접 돌린다.
헤드리스라 셰이더 컴파일은 빠진다 → [skills.md](skills.md) "히치 — 이펙트 풀".

## 스킬 이펙트 확인 (`fx-probe`) ★

**스크린샷은 사용자가 요청할 때만 찍는다.** 이펙트라고 예외가 아니다 — 토큰이 비싼 데다,
창이 가려지면 `requestAnimationFrame` 이 멈춰서 화면이 낡은 채로 굳는다. 그 상태로 찍으면
"이펙트가 안 나온다" 로 오진한다 (실제로 그렇게 한 바퀴 돌았다).

`SkillFx` 가 하는 일은 사실 전부 계산이다 — 어디에, 얼마나 크게, 어느 방향으로, 언제까지.
그래서 three 를 Node 에서 그대로 불러 `update(dt)` 를 돌리고 좌표를 찍는다.

```bash
npm run fx-probe                 # 할퀴기(rising_kick)
npm run fx-probe -- sky_breaker  # 스킬 id 를 주면 그것
npm run fx-probe -- white_tiger -90   # 셋째 인자는 캐릭터가 보는 각(도) — 옆모습 뒤집기 확인
npm run fx-probe -- hurt         # 스킬이 아닌 것: 캐릭터 피격
```

찍히는 것: 띄운 개수, 각각의 자리·크기·방향, 0.1초마다 **가장 먼 것까지의 거리**와
**그때의 밝기**, 그리고 언제 끝났는지.

- **사거리를 넘는지 여기서 잡는다.** 날아가는 이펙트가 몸 앞 0.6m 에서 출발하는 걸 빼먹어 3m 짜리가
  3.73m 까지 날아간 적이 있다 — 화면으로는 절대 못 봤을 오차다.
- **밝기가 도중에 0 으로 꺼지는지도 여기서 잡힌다.** 2026-09-07 "이펙트가 안 나온다"의
  원인이 그것이었다 ([skills.md](skills.md) 의 밝기 곡선).
- 안 되는 것은 **색과 그림의 생김새**뿐이다 — 다만 **지오메트리 생김새는 아래처럼 찍어 볼 수 있다.**
- 그림(스프라이트)은 `TextureLoader` 가 `document` 를 찾으므로 Node 에서 못 받는다.
  자리와 시간은 그대로 계산되고, 로그에는 "그림 N장" 으로만 센다.

## 지오메트리 생김새만 찍어 보기 ★

`fx-probe` 는 **어디에 얼마나 크게**까지만 알려 준다. 새로 만든 지오메트리가
**무슨 모양인지**는 그것으로 못 본다 — 그렇다고 게임을 띄워 스크린샷을 찍으면
접속·캐릭터·스킬 습득을 다 지나야 한다.

바닥에 눕는 것(금·고리·기운 줄기)은 **위에서 내려다본 그림이 곧 생김새**다.
three 를 Node 에서 불러 삼각형을 그대로 래스터로 찍으면 브라우저 없이 한 장이 나온다.
2026-09-16 천붕각 지진 바닥이 이렇게 확인됐다 — 처음 판은 조각이 **바퀴살처럼 늘어서**
있었고, 그건 글로는 절대 안 보였다.

**다만 굵기는 여기서 판단하면 안 된다.** 이 그림은 13m 를 420픽셀로 줄인 것이라 실제
화면(1080p 에 세로 21m)보다 촘촘하다. 반폭 0.07 짜리 틈이 여기서는 멀쩡해 보였는데
게임에서는 **흰 띠**였다 (2026-09-16). 굵기는 **미터로 계산해서** 본다 —
`반폭 × 2 × 사거리 ÷ 21 × 화면세로픽셀` 이 대략 몇 픽셀인지.

저장소 안에 두고 돌린다 (`three` 를 찾으려면 위치가 저장소 안이어야 한다).
다 보고 나면 지운다 — 대상이 매번 달라서 도구로 남길 만한 게 못 된다.

```js
import * as THREE from 'three';
import sharp from 'sharp';
THREE.TextureLoader.prototype.load = () => new THREE.Texture(); // 그림은 Node 에서 못 받는다
const { SkillFx } = await import('./packages/client/src/scene/skillFx.ts');
const fx = new SkillFx(); // private 필드도 런타임에는 그냥 읽힌다 (fx.fissureGeo …)

const S = 360, R = 6.6; // 화면 한 변 = 13.2m
const buf = Buffer.alloc(S * S * 3);
const px = (x, z, c) => {
  const i = (Math.round((z / R * 0.5 + 0.5) * S) * S + Math.round((x / R * 0.5 + 0.5) * S)) * 3;
  if (i >= 0 && i + 2 < buf.length) for (let k = 0; k < 3; k++) buf[i + k] = Math.min(255, buf[i + k] + c[k]);
};
const fill = (geo, scale, rotY, c) => {         // 삼각형을 무게중심으로 훑어 채운다
  const p = geo.getAttribute('position').array;
  const co = Math.cos(rotY), si = Math.sin(rotY);
  for (let t = 0; t < p.length; t += 9) {
    const v = [0, 1, 2].map((k) => [
      (p[t + k * 3] * co + p[t + k * 3 + 2] * si) * scale,
      (-p[t + k * 3] * si + p[t + k * 3 + 2] * co) * scale,
    ]);
    for (let a = 0; a <= 24; a++) for (let b = 0; a + b <= 24; b++) {
      const u = a / 24, w = b / 24, q = 1 - u - w;
      px(v[0][0] * q + v[1][0] * u + v[2][0] * w, v[0][1] * q + v[1][1] * u + v[2][1] * w, c);
    }
  }
};

for (let i = 0; i < 8; i++) fill(fx.fissureGeo, 6, (i / 8) * Math.PI * 2, [255, 190, 60]);
fill(fx.shockGeo, 6, 0, [60, 45, 15]);
await sharp(buf, { raw: { width: S, height: S, channels: 3 } }).png().toFile('logs/shape.png');
```

**색을 종류별로 다르게 준다.** 겹쳐 그리는 것이라 한 색으로 두면 어느 게 어느 건지
구분이 안 된다. 크기·각도는 이펙트를 띄우는 자리(`skyBreaker` 등)에서 쓰는 값을 그대로
옮겨 온다 — 다른 값으로 찍으면 확인한 게 아니다.

## 브라우저에서 이펙트만 띄우기 (`__skillFx`)

이펙트는 글로 읽을 수가 없는데, 실제로 쓰려면 서버 판정(직업·레벨·액션바)을 통과해야
한다. 천붕각은 Lv.150 이라 그러지 않으면 확인할 방법이 아예 없다. 그래서 **그리기만
하는** 전역 함수를 하나 뒀다 (`main.ts` 맨 아래). 서버로는 아무것도 안 가고 피해도 없다.

```js
__skillFx('sky_breaker')                          // 내 자리에 그 스킬 시전 이펙트만 띄운다
setInterval(() => __skillFx('sky_breaker'), 520)  // 한 장에 담으려면 반복시켜 둔다
```

- **렌더가 2~3 FPS 로 굳어 있으면 짧은 이펙트는 아예 못 본다.** 브라우저 창이 가려지면
  `requestAnimationFrame` 이 스로틀되는데, 그러면 한 프레임의 `dt` 가 0.4초라 0.4초짜리
  검기는 **거의 사라진 상태로 한 번 그려지고 끝난다.** 화면은 멀쩡해 보이므로 "이펙트가
  안 나온다" 로 오진하기 쉽다. 스크린샷을 **아주 작게(0.1배) 두세 장 연달아 찍으면**
  렌더가 깨어난다 — 그 다음 장을 제대로 된 크기로 찍는다. 토큰은 큰 거 한 장 값이다.
- **한 번 띄우고 찍으면 대개 빈 화면이 나온다.** 천붕각은 1.1초짜리인데 그중 발이
  떨어지는 건 0.3초다. 스크린샷 시점을 맞출 방법이 없으니 반복시켜 놓고 찍는다.
- **떴는데 안 보이는 경우는 픽셀로 잡는다.** `requestAnimationFrame` 을 감싸 게임이
  그린 **직후**에 캔버스의 `readPixels` 를 부르면 된다 (그냥 부르면 버퍼가 이미 비었다).
  이펙트가 뜬 프레임에서 밝은 픽셀 수가 몇 배로 뛰는지 보면 된다 — 천붕각은 기준
  9,000 → 최대 72,000 이었다. 예전에 "이펙트가 안 나온다" 로 하루를 쓴 게
  이 수치를 안 재서였다 ([skills.md](skills.md) 의 밝기 곡선).

## 스크린샷을 찍어도 되는 때

- 새로 만든 화면의 **모양**을 사람이 봐야 할 때 (레이아웃, 색, 겹침)
- 텍스트로 설명이 안 되는 시각 효과
- 그때도 **한 장**. 여러 번 찍어 비교해야 하면 그건 대개 `layout()` 으로 풀린다.

## 저장된 데이터를 건드리는 검증

"죽은 채로 재접속" 처럼 **DB 상태를 만들어야 하는 검증**은 돌아가는 서버의 DB 를
건드리지 말고, 임시 DB 로 서버를 하나 더 띄워서 한다. 둘 다 환경변수로 갈린다:

```bash
PORT=2599 DB_PATH=<임시경로>/test.db node src/index.ts   # packages/server 에서
```

- **`DB_PATH` 는 cwd 상대경로(`data/game.db`)다.** 서버는 `packages/server` 에서
  도니까 실제 파일은 `packages/server/data/game.db` 인데, 저장소 루트에서 스크립트를
  돌리면 `DB_PATH` 를 안 주는 순간 **루트에 빈 DB 를 새로 만들고 거기에 쓴다.**
  에러가 안 나서 검증이 통과한 것처럼 보인다 — 2026-09-07 에 이걸로 한 번 속았다.
- 고치기 전/후를 비교하려면 임시 서버 쪽 코드만 잠깐 되돌려 두 번 돌린다.
  같은 스크립트가 양쪽에서 다른 결과를 내야 원인이 맞다고 할 수 있다.

## 손댈 때

- 새 UI 창을 만들면 `ui-probe.js` 에 그 창을 뽑는 함수를 추가한다.
- 이펙트를 새로 만들면 `__skillFx` 로 띄워지는지 먼저 본다 — 서버 판정을 안 거치므로
  레벨·쿨타임·몬스터 없이 모양만 확인할 수 있다.
- 새 서버 메시지를 만들면 `probe.mjs` 의 `onMessage` 목록에 한 줄 추가한다.
  안 그러면 SDK 가 "onMessage() not registered" 경고만 뱉고 내용을 못 본다.
